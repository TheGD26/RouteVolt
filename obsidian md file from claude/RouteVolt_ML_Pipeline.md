# RouteVolt — Trip Energy Prediction Pipeline

## 1. Objective

Predict `energy_consumed_kwh` for an EV trip from trip, vehicle, environmental, traffic,
road, and elevation features. The target is **synthetic**, generated by
`generate_dataset.py` from an additive physics formula:

```
energy = (aero_term + elevation_term + rolling_term + traffic_term) × temp/weather_multipliers + ~3% relative noise
```

Two structural facts drove every modeling decision in this project:

- `distance_km` is a **direct multiplicative factor in 3 of 4 formula terms** → any
  reasonable model should find it dominant.
- `avg_speed_kmh` enters the aero term as **v² (speed-squared)** → this is the one
  nonlinearity a linear-in-log model cannot represent structurally, no matter how it's
  transformed. This became the central hypothesis tested across the whole project:
  *do tree models actually capture the v² term, or is the R² gap explained by something
  else?* The evidence (ablation + permutation importance, both re-run on the tuned final
  model) says yes, they capture it.

## 2. Dataset & Features

| Split | Rows | File |
|---|---|---|
| Train | 8,000 | `trip_energy_train.csv` |
| Test | 2,000 | `trip_energy_test.csv` (untouched until Step 9) |
| Full (pre-split) | 10,000 | `trip_energy_dataset.csv` |

> An earlier N=500 version (400/100 split) exists in `archive_n500/` — kept, not
> deleted, because it's a real finding in its own right (see §7).

**13 modeling features** (9 numeric + 4 categorical):

```
numeric:      distance_km, elevation_gain_m, elevation_loss_m, avg_speed_kmh,
              traffic_congestion_level, ambient_temperature_c,
              vehicle_battery_capacity_kwh, vehicle_efficiency_baseline_wh_per_km,
              total_mass_kg
categorical:  road_type, weather_condition, vehicle_profile, load_state
```

**Excluded, deliberately:**
- `trip_id` — identifier, no signal
- `wh_per_km` — **leakage** (derived from the target)
- `vehicle_curb_weight_kg`, `payload_kg` — redundant with `total_mass_kg` (their sum)

Split via `split_dataset.py`, stratified on `vehicle_profile × road_type × load_state`
so both splits share the same categorical mix.

## 3. Preprocessing — Two Pipelines

Linear models and tree models need different preprocessing, so two `ColumnTransformer`s
were built rather than one compromise pipeline:

```python
def build_preprocessors():
    log_scale_pipeline = Pipeline([
        ("log1p", FunctionTransformer(np.log1p)),
        ("scale", StandardScaler()),
    ])

    linear_preprocessor = ColumnTransformer([
        ("log_scale", log_scale_pipeline, log_transform_features),   # distance_km, elevation_gain_m, elevation_loss_m
        ("scale_only", StandardScaler(), scale_only_features),        # remaining numeric
        ("onehot", OneHotEncoder(handle_unknown="ignore"), categorical_features),
    ])

    tree_preprocessor = ColumnTransformer([
        ("passthrough", "passthrough", numeric_features),   # trees don't need scaling
        ("onehot", OneHotEncoder(handle_unknown="ignore"), categorical_features),
    ])

    return linear_preprocessor, tree_preprocessor
```

- **`linear_preprocessor`**: right-skewed features (`distance_km`, elevation) get
  `log1p` + `StandardScaler`; everything else gets `StandardScaler`; categoricals get
  one-hot. Linear models are sensitive to feature scale and skew — trees are not.
- **`tree_preprocessor`**: numeric features pass through untouched (splits are
  scale-invariant); categoricals still need one-hot since sklearn trees don't natively
  handle categorical strings.

`build_linear_preprocessor(numeric_cols, categorical_cols, log_cols)` is a
parameterized twin of the linear half, used whenever a **feature subset** needs its own
preprocessor (leave-one-out ablation, where the dropped column must not appear in any
transformer). `build_tree_preprocessor(numeric_cols, categorical_cols)` is the same idea
for the tree side, used in the HGB-specific ablation (§8).

## 4. Function-by-Function Reference (`train_model.py`)

### Data loading
- **`load_data()`** — reads `trip_energy_train.csv`, returns `(X, y)` restricted to the
  13 modeling features + target.
- **`load_test_data()`** — sibling function reading `trip_energy_test.csv`. Kept
  deliberately separate from `load_data()` (not a `path` parameter) so it's visually
  obvious in `main.py` exactly where the untouched test set gets touched.

### Evaluation harnesses
- **`evaluate_model(X, y, model, preprocessor=None)`** — the main workhorse. Wraps
  `model` in a `Pipeline` with `preprocessor` (if given), runs
  `cross_validate(..., cv=KFold(5, shuffle=True, random_state=42))` scoring MAE, RMSE,
  R² simultaneously, and returns `{metric}_mean` / `{metric}_std` for each. Used for
  every **raw-target** evaluation (trees, and the `TransformedTargetRegressor`-wrapped
  linear models — see below).
- **`evaluate_model_log_target(X, y_raw, model, preprocessor=None)`** — manually
  log1p-transforms `y`, gets out-of-fold predictions via `cross_val_predict`, inverts
  with `expm1`, then scores once (not per-fold) with `mean_absolute_error`,
  `root_mean_squared_error`, `r2_score`. **Historical**: this was the original way
  log-target linear models were evaluated, before being superseded (see §5) — still used
  by `run_ablation` and `run_residual_analysis` for the Ridge-based checks.
- **`evaluate_model_log_target_with_preds(...)`** — same as above but also returns the
  raw predictions array, needed by `run_residual_analysis` to compute residuals.

### Comparison / diagnostic functions (Steps 2–6)
- **`run_baselines(X, y, linear_preprocessor)`** — evaluates `LinearRegression` and
  `Ridge` via `evaluate_model_log_target`.
- **`run_ablation(X, y, linear_preprocessor)`** — leave-one-out feature ablation on
  Ridge: drops one numeric column at a time, rebuilds a matching preprocessor via
  `build_linear_preprocessor`, re-evaluates, and prints R² sorted ascending. This is
  the **Step 5 leakage investigation** — confirmed `distance_km` alone drives
  ~0.38 of R², `vehicle_battery_capacity_kwh` contributes ~0 (not in the true formula).
- **`run_residual_analysis(X, y, linear_preprocessor)`** — fits Ridge, computes
  residuals, correlates `|residual|` against each numeric feature. Showed the largest
  absolute errors concentrate on long, high-speed trips — the signature of a linear
  model failing to represent the v² aero term.
- **`run_tree_comparison(X, y, tree_preprocessor)`** — evaluates
  `RandomForestRegressor` and `HistGradientBoostingRegressor` at both raw-y and
  log-y target space (raw wins for both — trees don't need variance stabilization, and
  log/expm1 back-transform introduces bias trees don't need). Also runs the
  residual-vs-feature correlation check for RF/HGB, and a hand-constrained RF
  (`min_samples_leaf=5`) that was tested as a naive regularization guess and made
  things **worse** — the finding that motivated real hyperparameter search over
  guessing (Step 7).
- **`run_log_target_wrapper_comparison(X, y, linear_preprocessor)`** — the retired
  dual-evaluator problem's replacement: wraps `LinearRegression`/`Ridge` in
  `TransformedTargetRegressor(func=np.log1p, inverse_func=np.expm1)` so they run
  through the same `evaluate_model()` as everything else — fully comparable
  mean±std across all five models in one table (§6).

### Hyperparameter tuning (Step 7)
- **`run_rf_tuning(X, y, tree_preprocessor)`** — `RandomizedSearchCV` (40 iterations,
  same fixed `KFold`, `scoring="r2"`, `n_jobs=-1`) over:
  ```python
  {"model__n_estimators": randint(100, 600),
   "model__max_depth": [None, 10, 20, 30],
   "model__min_samples_leaf": randint(1, 10),
   "model__max_features": ["sqrt", "log2", None]}
  ```
  Prints and returns the fitted `RandomizedSearchCV` object (kept whole, not just
  `best_estimator_`, so `cv_results_` stays available for diagnostics later).
- **`run_hgb_tuning(X, y, tree_preprocessor)`** — structurally identical, tuning
  `HistGradientBoostingRegressor` over:
  ```python
  {"model__learning_rate": loguniform(0.01, 0.3),
   "model__max_iter": randint(100, 500),
   "model__max_leaf_nodes": randint(15, 63),
   "model__min_samples_leaf": randint(5, 50)}
  ```

### Post-tuning sanity check (Step 8, pre-decision)
- **`run_hgb_ablation(X, y, hgb_search, tree_preprocessor)`** — re-runs the Step 5-style
  leave-one-out ablation, but on the **tuned HGB model** (params extracted from
  `hgb_search.best_params_`) instead of Ridge. This existed to answer one specific
  question before trusting the tuned R²: tuned HGB scored 0.9917, above the ~0.976
  ceiling the linear/log-additive structure implied — was that legitimate, or an
  artifact? The ablation confirmed `distance_km` (+0.4555 R² if dropped) and
  `avg_speed_kmh` (+0.0664) still dominate, even more cleanly than for Ridge —
  consistent with HGB genuinely capturing the v² term, not exploiting anything spurious.

### Final evaluation (Step 9)
- **`run_final_test_evaluation(X_train, y_train, X_test, y_test, hgb_search, tree_preprocessor)`**
  — the one genuinely different function in the file: **no cross-validation**. Fits the
  tuned HGB pipeline once on all 8,000 training rows, predicts once on the 2,000-row
  untouched test set, scores once. Returns `(final_pipeline, test_metrics)` so Step 10
  can reuse the fitted model without refitting.

### Interpretation (Step 10)
- **`run_permutation_importance(final_pipeline, X_test, y_test)`** — since
  `HistGradientBoostingRegressor` has no native `.feature_importances_`, importance is
  computed by shuffling one original (pre-encoding) column at a time on the test set and
  measuring the R² drop (`n_repeats=20`, `scoring="r2"`). Run at the **original-column**
  level (not per one-hot dummy) so results map onto meaningful features like
  `road_type` as a whole.

## 5. Evaluation Metrics — What They Mean Here

| Metric | Meaning | Notes for this project |
|---|---|---|
| **R²** | Fraction of target variance explained | Primary comparison metric, but never trusted alone — every R² number here is paired with a std across 5 folds, and cross-checked against ablation/permutation importance before being trusted |
| **MAE** | Mean absolute error, in kWh | More interpretable "typical error size" than R²; final model: 0.97 kWh on test |
| **RMSE** | Root mean squared error, in kWh | Penalizes large errors more than MAE; gap between RMSE and MAE indicates some trips have disproportionately large errors (the long/high-speed trips flagged in residual analysis) |
| **R²_std / MAE_std** (cross-val) | Std across the 5 fixed folds | Used as a **stability** signal, not just accuracy — e.g. HGB's fold variance dropping ~25x between N=500 and N=10k was as important a finding as the R² number itself |

**Cross-validation setup**: every single evaluation in this project — baselines,
ablation, tree comparison, tuning — uses the exact same `KFold(n_splits=5, shuffle=True,
random_state=42)`. Because the seed is fixed, every model in every comparison table is
scored on the **same five folds**, making every R² comparison a legitimate paired
comparison rather than independently-noisier runs. (Declined: an additional multi-seed
robustness check, as an explicit deadline trade-off — noted as a limitation, not
silently skipped.)

## 6. Model Comparison — Full History

### N=500 (early, archived) — linear models won
| Model | R² |
|---|---|
| Ridge / Linear | 0.977–0.978 |
| RF | 0.940 |
| HGB | 0.916 (R²_std = 0.052 — high variance) |

Hypothesis at the time: this was a small-data artifact, since the target has a real
v² nonlinearity linear models structurally can't represent. Tested by regenerating at
N=10,000 with the same RNG seed/formula — **hypothesis confirmed** below.

### N=10,000 — untuned, Step 4 table
| Model | Target space | R²_mean | R²_std | MAE_mean |
|---|---|---|---|---|
| LinearRegression | log (TransformedTargetRegressor) | 0.9762 | 0.0022 | 1.859 |
| Ridge | log (TransformedTargetRegressor) | 0.9761 | 0.0023 | 1.863 |
| RF | raw | 0.9850 | 0.0039 | 1.402 |
| **HGB** | raw | **0.9907** | **0.0021** | **1.046** |

HGB's fold variance dropped ~25x vs the N=500 run (0.052 → 0.0021) — strong evidence the
earlier instability was a data-size problem, not an inherent HGB weakness.

### N=10,000 — tuned (Step 7 results)
| Model | R²_mean (untuned → tuned) | R²_std (untuned → tuned) | Verdict |
|---|---|---|---|
| RF | 0.9850 → 0.9850 | 0.00393 → 0.00389 | **No improvement.** Best params landed near defaults (`min_samples_leaf=1`, `max_features=None`) — the search independently rediscovered that constraining RF hurts (matches the earlier hand-picked `min_samples_leaf=5` finding, which scored worse: R²=0.9818). Reported as a legitimate negative result, not hidden. |
| HGB | 0.9907 → **0.9917** | 0.00214 → **0.00097** | **Real improvement**, mostly in stability (fold variance roughly halved) rather than raw accuracy. Best params: `learning_rate≈0.170`, `max_iter=393`, `max_leaf_nodes=16`, `min_samples_leaf=25`. |

**Decision (Step 8): final model = tuned HistGradientBoostingRegressor.** Chosen for
best mean R², best (lowest) fold variance, and — critically — confirmed via the Step 8
ablation sanity check (§4) that its performance is grounded in the same real physics
signal (`distance_km`, `avg_speed_kmh`) rather than something spurious.

## 7. Step 9 — Untouched Test Set Result

```
Final HGB — untouched test set: {'MAE': 0.9735, 'RMSE': 2.3518, 'R2': 0.9920}
```

Compared to the CV estimate (R²=0.9917, std=0.00097): the test R² (0.9920) lands well
within one fold-std of the CV mean. This is the important confirmation — it means the
extensive hyperparameter search (80 total fits across RF+HGB) did **not** quietly
overfit to the specific 5 CV folds, and the model generalizes to genuinely unseen data
at the same level it appeared to during tuning.

## 8. Step 10 — Interpretation

Permutation importance (test set, `n_repeats=20`, mean R² drop when a feature is
shuffled):

| Feature | Importance | |
|---|---|---|
| `distance_km` | 1.3206 | dominant, as expected — literal multiplicative factor in 3/4 formula terms |
| `avg_speed_kmh` | 0.2620 | second, and the feature carrying the v² nonlinearity trees capture and linear models can't |
| `total_mass_kg` | 0.0193 | small but real |
| `traffic_congestion_level` | 0.0159 | small but real, matches its role as a formula term |
| `vehicle_battery_capacity_kwh` | 0.0099 | **see caveat below** |
| `ambient_temperature_c` | 0.0087 | small but real, matches its role as a multiplier |
| `weather_condition` | 0.0019 | negligible |
| `road_type` | 0.0018 | negligible |
| `vehicle_profile` | 0.0003 | negligible |
| `load_state` | 0.0003 | negligible |
| `elevation_gain_m` | 0.0001 | negligible |
| `vehicle_efficiency_baseline_wh_per_km` | 0.0000 | negligible |
| `elevation_loss_m` | -0.0003 | negligible / noise-level (slightly negative is not meaningful at this scale) |

**Important caveat — correlation vs. causation**: `vehicle_battery_capacity_kwh` shows
nonzero permutation importance (0.0099) despite the Step 5/8 ablations both confirming
it contributes ~0 when *dropped entirely*. The likely explanation: it's correlated with
`vehicle_profile`/`vehicle_efficiency_baseline_wh_per_km` (bigger vehicles → bigger
batteries → different baseline efficiency, by construction of the synthetic generator).
Permutation importance breaks that correlation when shuffling, which shows up as fake
importance for a feature the model isn't actually causally using — it's reconstructing
the same information from correlated features that remain intact. **Ablation is the more
causally honest signal here; permutation importance measures something closer to
"how much predictive information passes through this feature," which is not the same
as "how much does this feature matter physically."**

## 9. Known Limitations (documented, not hidden)

- No multi-seed CV robustness check — declined as an explicit deadline trade-off, all
  results rest on a single `random_state=42` fold split.
- R² ≈ 0.97–0.99 across the board reflects a **low-noise, near-log-additive synthetic
  target**, not genuine predictive difficulty — confirmed via the Step 5 leakage
  investigation, not a red flag being ignored.
- Elevation features (`elevation_gain_m`, `elevation_loss_m`) show negligible
  importance in this dataset — plausibly because trip-level elevation variance is small
  relative to distance/speed variance in the generator, not evidence the underlying
  physics term is wrong.
