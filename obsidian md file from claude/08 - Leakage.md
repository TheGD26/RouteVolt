#RouteVolt #leakage

Back to [[00 - RouteVolt Master Map]] · Previous: [[07 - ML Pipeline]]

> [!info] Why this note matters most for RouteVolt specifically
> Because the target (`energy_consumed_kwh`) is planned to be generated by a **known formula you write yourself** (see [[04 - Target Generation]]), RouteVolt has an unusually acute leakage risk that a project using *measured* real-world data wouldn't have in the same way: it's trivially easy to accidentally build a "model" that's just re-deriving your own formula, which teaches you nothing about ML and gives a false sense of accuracy.

## Formula leakage

**Definition:** When the target is a deterministic (or near-deterministic) function of the features, and the model essentially "solves for" that function rather than learning a generalizable pattern.

**RouteVolt example:** If `energy_consumed_kwh = distance_km × wh_per_km(conditions)` is applied with **no noise term** (see [[04 - Target Generation]] Stage 8), a sufficiently flexible model (or even a modest one) can reconstruct the formula almost exactly, achieving R² ≈ 1.0.

**Why it's dangerous:** It hides whether your feature set and model architecture would work on *real, noisy* data. It also makes every part of [[07 - ML Pipeline]]'s evaluation (baseline comparison, feature importance) meaningless, because the model isn't doing anything interesting — it's just formula inversion.

**How to detect it:** Suspiciously high R² (>0.98) with very low residual variance; residuals that show no pattern *because there's nothing left to explain*; a simple model (e.g., shallow decision tree) performing nearly as well as a complex one.

**How to prevent it:** Always include the random noise term (Stage 8 in [[04 - Target Generation]]) at a magnitude large enough to leave meaningful residual variance — calibrate σ so that even the "true" formula, if you had access to it, couldn't achieve R² > ~0.95-0.97 on held-out data.

## Target leakage

**Definition:** A feature that is only available *because* the target already happened, or that encodes the target (or something derived from it) directly.

**RouteVolt example:** If `wh_per_km` were accidentally included as a feature (X) when predicting `energy_consumed_kwh` (y), the model would trivially learn `energy = wh_per_km × distance / 1000` — which is just re-deriving the definitional relationship in [[04 - Target Generation]] Stage 9, not learning anything.

**Why it's dangerous:** Perfect accuracy in training/testing, complete failure in a real deployment where `wh_per_km` for an *unstarted* trip obviously isn't known yet — it's the thing you're trying to predict, restated.

**How to detect it:** Near-perfect scores combined with one feature having overwhelmingly dominant importance.

**How to prevent it:** Explicitly exclude `wh_per_km` from X when training on `energy_consumed_kwh` as y (and vice versa) — treat them as two views of the same target, never mix one into the features for the other.

## Feature leakage

**Definition:** A feature that wouldn't actually be knowable *at prediction time* (before or during the real trip), even if it's legitimately correlated with the target in the training data.

**RouteVolt example:** The `avg_speed_kmh` timing tension flagged in [[01 - Feature Map]] — if this is meant to represent the *actual observed* average speed of a completed trip (rather than a forecast/planned speed), using it to predict energy consumption *before the trip happens* is feature leakage: at prediction time, you don't yet know how fast the trip will actually go, only what you plan or forecast.

**Why it's dangerous:** The model looks great in offline evaluation (where the "future" `avg_speed_kmh` is already in the historical row) but can't actually be used in the real RouteVolt app, where `optimize_route()` needs a prediction *before* the drive starts.

**How to detect it:** Ask, for every feature, "would this value exist in the app's database at the moment the user requests a route recommendation, before driving?" Any "no" is a leakage candidate.

**How to prevent it:** Either (a) redefine the feature as a *forecast/planned* value (e.g., "expected average speed from a traffic API for this route right now"), or (b) remove it from the feature set and accept the model will be somewhat less accurate but actually deployable.

## Snapshot/static-value leakage

**Definition:** A feature captured as a static snapshot that implicitly bakes in information from a time *after* the point at which a real prediction would be made.

**RouteVolt example:** `traffic_congestion_level` — if this is generated to represent congestion *during* the trip (rather than *forecast* congestion *before* the trip starts), it's a snapshot of a future/in-progress state being used as if it were known in advance. Similarly, if `charging_stations.csv`'s `queue_time_minutes` were ever folded into the trip model, using a queue time *observed after arrival* to predict *pre-trip* recommendations would be the same failure mode.

**Why it's dangerous:** Same as feature leakage above, but sneakier because it's often a single "innocent-looking" numeric column rather than an obviously time-traveling feature.

**How to detect it:** Trace each feature back to *when*, physically, that value would be known — sampling-time convenience (it was easy to generate a `traffic_congestion_level` for the whole trip) does not mean it reflects real prediction-time availability.

**How to prevent it:** Be explicit in the generator's design about whether each condition column represents a *pre-trip forecast* or a *during/post-trip observation*, and only use forecast-type columns as prediction features for a pre-trip recommendation system.

## Generator leakage

**Definition:** The generator itself encodes a strong, artificial correlation between two features that has no real-world basis, which the model then "discovers" and treats as signal — a form of leakage from *design choices* rather than from timing.

**RouteVolt example:** If the sampler ties `road_type` and `avg_speed_kmh` *too rigidly* (e.g., "highway" always maps to exactly 90-100 km/h with almost no variance), the model doesn't need to learn anything about speed's physical effect on drag — it can just memorize "if road_type == highway, use this energy value," collapsing what should be a continuous physical relationship into a categorical lookup.

**Why it's dangerous:** Makes the model brittle and unrealistic — real highway driving varies a lot in average speed (congestion, weather, driver behavior), and a model trained on an artificially rigid mapping won't generalize even to slightly different synthetic data, let alone real data later.

**How to detect it:** Check conditional variance — for each `road_type`, is there meaningful spread in `avg_speed_kmh`, or does it collapse to a near-constant? (Ties into [[06 - Data Validation]] checks 1 and 3.)

**How to prevent it:** When designing correlated sampling distributions (per [[05 - Synthetic Dataset]]), always use a distribution with real variance (e.g., a normal or beta distribution around a road-type-specific mean), never a fixed lookup value.

## The core danger, restated

`y = exact_deterministic_formula(X)` trained without noise produces a model that is, at best, a slow and expensive way to recompute a formula you already know, and at worst, a model that silently fails the moment it meets real-world variance it was never exposed to. **Noise and realistic variation aren't optional polish — they're what makes the ML step of this project meaningful at all**, rather than a roundabout way of re-implementing [[04 - Target Generation]] in scikit-learn.
